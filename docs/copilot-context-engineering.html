Speaking Copilot's Language

GitHub Copilot searches and reads your code to assemble context for a task. Your prompt, instructions, conversation history, and tool results share a finite context window. Explore one flow, verify the explanation, and preserve what you learn. This sheet holds six files ready to copy.

Three scopes, and which paths belong to each

Settle the geography before the tiers. The same paragraph of instruction text does a different job depending on whether you keep it in your own profile, commit it to the repository, or set it once for the whole organization. GitHub and VS Code document the same order of priority, and it runs from personal down to organization.

Scope Where it goes Who it reaches
1. PersonalHighest priority ~/.copilot/instructions
~/.claude/rules		 Only you, in every workspace on the machine. Create one with the Chat: New Instructions File command. Settings Sync carries these between machines if you select Prompts and Instructions in Settings Sync: Configure.
2. RepositoryMiddle priority .github/copilot-instructions.md
.github/instructions/*.instructions.md
.github/prompts/*.prompt.md
AGENTS.md		 Everyone who clones the repository, reviewed in pull requests like any other code. This is the scope the rest of this sheet is about, because it's the only one that survives a new hire.
3. OrganizationLowest priority Set by organization owners in the organization's Copilot settings on GitHub.com. Requires Copilot Business or Copilot Enterprise. Every member of the organization, on Copilot Chat and Copilot code review on GitHub.com.

A folder isn't a fourth scope. It's a property of the file. A tier 2 file scopes itself with its applyTo glob, which is the supported way to say this applies to the payments folder and nothing else. VS Code will also read nested AGENTS.md files in subfolders when chat.useNestedAgentsMdFiles is enabled, and the documentation marks that setting experimental, so don't write a standard around it yet.

The precedence you just read is by scope, not by file. Personal beats repository, and repository beats organization. Inside one repository it's a different story: VS Code documents that it combines the instruction files it finds and that no specific order is guaranteed. So don't write two repository files that contradict each other and expect a tiebreak. Write them so they compose.

Instructions and administrative policy are different controls. Instruction precedence does not override organization permissions, tool restrictions, or other enforced settings. Check the documentation for the specific client before relying on a priority rule.

Choose when the guidance is needed

These four teaching categories help you decide where to put knowledge. They describe loading and purpose, not a universal priority order across every Copilot feature.

TierWhere it goesHow it is usedBudget habit
1. Repository-wide.github/copilot-instructions.md
AGENTS.md		Included for workspace chat when supported and enabled.Keep essential guidance short.
2. Scoped.github/instructions/*.instructions.mdApplied to relevant files or tasks; these examples use applyTo patterns.Load subsystem detail where it applies.
3. Invoked.github/prompts/*.prompt.mdYou invoke a repeatable task such as /trace-flow.Reuse the investigation method.
4. Procedural.github/skills/<name>/SKILL.mdDiscovery metadata helps the agent select the skill; its body loads when selected or invoked.Keep discovery concise and load details on demand.

Verify the actual client. Settings, feature support, and organization policies affect instruction discovery. Inspect the applied customizations and tool activity. A short instruction can guide an investigation; it does not guarantee a correct answer.

Tier 1: always loaded

Two files, both repository-wide. Between them, keep the total under roughly a page.

.github/copilot-instructions.md

Repository-wide guidance for supported Copilot Chat clients with instructions enabled.

AGENTS.md

Repository root. Shared conventions for supported agents. Check the documentation and settings for the client or review feature you use; support is not identical across every surface.

Tier 2: conditionally loaded, and the one to build first

The applyTo glob scopes these instructions to relevant paths. Keep Ordering details with Ordering work instead of adding them to every request. This is also how the technique survives on a small repository: scope by layer or by language instead of by service.

.github/instructions/ordering.instructions.md

.github/instructions/tests.instructions.md

Verify scope before you trust it. Open a file inside the glob and confirm the instructions are in play, then open one outside it and confirm they aren't. A glob that silently matches nothing looks identical to a glob that works.

Copilot Spaces: the distinction that's expensive to get wrong

Spaces bring in what your team knows but never committed to the repository: wikis, Markdown, decision records, specs. How you attach a source decides what it costs.

Attach a whole repository

Content is searched selectively and retrieved on demand. It costs you only when the retrieval step decides it's relevant.

Use for: everything you might need.

Attach individual files

Individual files provide focused context for the Space's questions. Choose the small set that defines the subsystem and check which sources support each answer.

Use for: the few documents that should always be true.

GitHub is explicit that not everything in a Space is necessarily used for every answer, so treat a Space as a curated candidate pool rather than a guarantee.

Check the date on your internal guidance. Copilot knowledge bases were retired on November 1, 2025 and replaced by Copilot Spaces, with a conversion path for existing ones. If a runbook or onboarding doc still tells your team to create a knowledge base, that guidance needs a currency check before reuse.

Understand a large codebase one flow at a time

Start with a business action you can name. A bounded question gives you an explanation you can verify and a manageable set of files to inspect.

Check access and search before judging the answer

Current VS Code guidance describes automatically maintained semantic indexes. Inspect indexing status in the Copilot status dashboard. When needed, the documented command is Build Codebase semantic index. Availability depends on the repository, account, and policy. Even without a semantic index, agents can use text search, file search, and language intelligence. An unavailable index does not mean the agent is unable to investigate.

Do not use historical 750/2,500-file cutoffs as a current troubleshooting rule. The current workspace-context documentation describes the behavior to check. Repository size, search scope, tool output, and model behavior can all affect the experience; measure the symptom before assigning a cause.

Give the investigation useful boundaries

  • Name the flow and known symbols. Include an entry point, method, event, or file when you know one. Ask for each hop and the evidence supporting it.
  • Reduce irrelevant search results. Review .gitignore, files.exclude, and search.exclude. Generated output can overwhelm useful matches, but excluding a file you need can also hide evidence.
  • Open the repository root for this lesson. If you work from a subfolder, check chat.useCustomizationsInParentRepositories so parent instructions are discoverable.
  • Read the source directly when necessary. Search-index exclusions are not a complete description of what an agent can access through file-reading and other tools.

Build understanding and instructions together

  1. Explore: use /trace-flow on one business action.
  2. Verify: follow the cited files, inspect tool activity, and check the explanation.
  3. Preserve: capture only verified conventions and dependencies in a short, appropriately scoped instruction.
  4. Reuse: investigate another flow and check whether the guidance improves the work.

You do not need to understand the whole application before beginning. The map and the instruction layer develop together, one checked explanation at a time. Keep assumptions visible so they do not become permanent instructions by accident.

The sample already includes guidance. Repeating the Ordering question here is not an instruction-free comparison. Finding a warning is useful, but it does not reproduce a defect. In this example, distinguish numeric Buyer.Id and Payment.Id from the integration event's BuyerIdentityGuid. Follow the README investigation to check the evidence.

Spend the budget on purpose

Give the next request the context it needs to answer the current question.

  1. Review explicit and editor context. Attach the relevant files or selection and remove irrelevant attachments. Do not assume every open tab is included in full.
  2. Start a fresh chat when the topic changes. Preserve verified conclusions in repository files instead of relying on a long conversation.
  3. Keep always-on guidance short. Move subsystem details and procedures into scoped instructions and skills. Large search results and tool outputs also consume context.

Diagnose the answer from its evidence

  1. Check references and tool activity. Which files were searched or read? Open them and verify the claims. The displayed references alone are not a complete causal diagnosis.
  2. If evidence is missing, narrow the investigation. Name a path or symbol, check access and exclusions, or explicitly request a file read.
  3. If the evidence was misinterpreted, challenge the reasoning. Ask how the cited lines support the conclusion and which assumptions remain. Adjust instructions if a durable investigation rule is missing.
  4. If results appear stale, check the actual checkout and index status. Do not assume every context problem is indexing lag.
  5. Evaluate model choice with the same evidence criteria. Compare correctness, coverage, and uncertainty on representative questions.

Read the budget instead of arguing about it

Everything on this sheet rests on one claim: context is a finite budget and you are already spending it. GitHub Copilot CLI will print that budget on request, which turns the claim into a receipt. If one engineer on your team stays skeptical, this is the fastest way to settle it.

The /context command reports the active model and the tokens in use against that model's total capacity, itemized:

Line itemWhat it tells you
System PromptFixed overhead. You don't control it.
Custom InstructionsThe files on this sheet. Your instruction layer is billed on its own line, separately from the conversation.
System ToolsTool definitions are charged whether or not you call them.
MCP ToolsSame rule, for anything you connected yourself.
MessagesYour turns, the responses, and every tool call and result. This is the line that grows.
Free SpaceWhat's left to work with.
BufferHeld back on purpose. See below.

At roughly 80 percent of capacity the CLI starts compacting in the background and holds back a buffer of roughly 20 percent so tool calls can keep running while it works. If usage reaches about 95 percent before compaction finishes, it pauses and waits. /compact does the same job on demand: it summarizes the conversation and replaces the history with that summary.

Two things to settle before you build on this. An organization can turn the Copilot CLI off in policy, so confirm your own tenant before you write it into a standard. And compaction is lossy by design, because a summary is smaller than what it replaced. A tight instruction layer spends less of the window in the first place, which pushes that summarization further away.

Measure whether the explanation helped

For this lesson, success means a student can explain the flow with evidence and apply the method to another flow. A longer answer or an accepted suggestion is not enough.

Useful evidence

Correct file and method references, accurate boundaries, distinguished identifiers, checked warnings, and explicit unknowns.

What usage cannot prove

License counts and chat activity alone do not establish understanding or correctness. Pair any adoption measures with reviewed work and learner feedback.

Repeat the investigation on a different flow. Record what improved and what still needs human checking. That gives you a concrete basis for refining the instructions.
