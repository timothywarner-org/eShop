Speaking Copilot's Language

GitHub Copilot doesn't read your repository. It retrieves from it, and everything it retrieves competes for the same finite context window as your prompt, your open files, and your chat history. This sheet holds every file we built during the session, ready to copy.

Three scopes, and which paths belong to each

Settle the geography before the tiers. The same paragraph of instruction text does a different job depending on whether you keep it in your own profile, commit it to the repository, or set it once for the whole organization. GitHub and VS Code document the same order of priority, and it runs from personal down to organization.

Scope Where it goes Who it reaches
1. PersonalHighest priority ~/.copilot/instructions
~/.claude/rules		 Only you, in every workspace on the machine. Create one with the Chat: New Instructions File command. Settings Sync carries these between machines if you select Prompts and Instructions in Settings Sync: Configure.
2. RepositoryMiddle priority .github/copilot-instructions.md
.github/instructions/*.instructions.md
.github/prompts/*.prompt.md
AGENTS.md		 Everyone who clones the repository, reviewed in pull requests like any other code. This is the scope the rest of this sheet is about, because it's the only one that survives a new hire.
3. OrganizationLowest priority Set by organization owners in the organization's Copilot settings on GitHub.com. Requires Copilot Business or Copilot Enterprise. Every member of the organization, on Copilot Chat and Copilot code review on GitHub.com.

A folder isn't a fourth scope. It's a property of the file. A tier 2 file scopes itself with its applyTo glob, which is the supported way to say this applies to the payments folder and nothing else. VS Code will also read nested AGENTS.md files in subfolders when chat.useNestedAgentsMdFiles is enabled, and the documentation marks that setting experimental, so don't write a standard around it yet.

The precedence you just read is by scope, not by file. Personal beats repository, and repository beats organization. Inside one repository it's a different story: VS Code documents that it combines the instruction files it finds and that no specific order is guaranteed. So don't write two repository files that contradict each other and expect a tiebreak. Write them so they compose.

If you also run Claude Code, this order is upside down from the one you know. Claude Code puts managed organization settings at the top of its precedence list, above the command line, above the project, above the user. Copilot does the reverse: personal wins, organization loses. An administrator who expects an organization-level instruction to be the final word will be right in one of these two products and wrong in the other, so establish which product you are arguing about before you argue about whose rule applies.

The only thing that distinguishes the four tiers is when content enters the window

Every artifact below does the same job: it tells Copilot what you care about. What separates them is when they get charged against your budget. Get this straight and the rest of the sheet is obvious.

Tier Where it goes Enters the window when What it costs you
1. Always .github/copilot-instructions.md
AGENTS.md		 Every request in the repository, no exceptions Charged every time. Keep these short or they become a tax.
2. Conditionally .github/instructions/
  *.instructions.md		 The applyTo glob matches a file in scope Nothing until you're in that part of the tree. Start here.
3. On request .github/prompts/
  *.prompt.md		 You type /name in chat Nothing until invoked. Turns folklore into a command.
4. On relevance .github/skills/<name>/
  SKILL.md		 The agent reads your description and decides it applies Nothing until it loads. The description does the work.

The mistake that costs the most: growing copilot-instructions.md into four hundred lines of coding standards. Every word in a tier-1 file displaces retrieved code on every single request, including the requests where those standards are irrelevant. If it wouldn't survive being read aloud, move it to tier 2.

Tier 1: always loaded

Two files, both repository-wide. Between them, keep the total under roughly a page.

.github/copilot-instructions.md

Applies to every Copilot Chat request in this repository.

AGENTS.md

Repository root. Read by VS Code, by coding agents, and by Copilot code review (generally available since June 18, 2026), so conventions written here also shape the review comments on your pull requests.

Tier 2: conditionally loaded, and the one to build first

The applyTo glob is what makes this tier free. Instructions for the ordering service cost you nothing while you're working in catalog. This is also how the technique survives on a small repository: scope by layer or by language instead of by service.

.github/instructions/ordering.instructions.md

.github/instructions/tests.instructions.md

Verify scope before you trust it. Open a file inside the glob and confirm the instructions are in play, then open one outside it and confirm they aren't. A glob that silently matches nothing looks identical to a glob that works.

Copilot Spaces: the distinction that's expensive to get wrong

Spaces bring in what your team knows but never committed to the repository: wikis, Markdown, decision records, specs. How you attach a source decides what it costs.

Attach a whole repository

Content is searched selectively and retrieved on demand. It costs you only when the retrieval step decides it's relevant.

Use for: everything you might need.

Attach individual files

That content is in play on every query against the Space, whether it helps or not. Same economics as a tier-1 instruction file.

Use for: the few documents that should always be true.

GitHub is explicit that not everything in a Space is necessarily used for every answer, so treat a Space as a curated candidate pool rather than a guarantee.

Check the date on your internal guidance. Copilot knowledge bases were retired on November 1, 2025 and replaced by Copilot Spaces, with a conversion path for existing ones. If a runbook or onboarding doc still tells your team to create a knowledge base, that document is more than a year stale and worth an owner.

“This monorepo is too big to understand in one bite”

Check which index Copilot is using before you change anything else. A workspace over 2,500 indexable files falls back to a basic index that searches with simpler algorithms, and the fallback is silent. That one fact accounts for more weak monorepo answers than model choice, prompt wording, and instruction files put together.

A large repository doesn't slow Copilot down in any way you can feel. What it does is lower the odds that the retrieval step hands back the five files your question actually needed. Same model, same latency, worse hit rate. So a conversation that opens with let's go evaluate something else is solving for the wrong variable, and it'll cost you a quarter before anyone notices.

Which index you are actually on

VS Code selects the index by counting indexable files in the workspace, and the Copilot status dashboard in the Status Bar reports which one you got. Open it on your own monorepo before the first slide of any internal enablement session. The room goes quiet.

IndexHow you get itWhat it gives you
Remote Run GitHub Copilot: Build Remote Workspace Index from the Command Palette. Needs a git remote on GitHub. Once per repository. Semantic search that holds up on large codebases. GitHub refreshes it as you push.
Local Automatic under 750 indexable files. Between 750 and 2,500, run Build local workspace index once. Fast, high quality, stored on your machine. The ceiling is 2,500 indexable files.
Basic What you get past 2,500 files when no remote index exists. Simpler search algorithms. Nobody chose this. It is where most monorepos sit, and it is the answer to “why is Copilot worse on our repo.”

Build the remote index and the file-count ceiling stops mattering. The catch worth saying out loud to a monorepo team is the refresh condition: the remote index tracks pushed code on the default branch. A long-lived unpushed branch is invisible to retrieval no matter how good your instruction files are, which is why “push regularly” is GitHub's own written remedy for stale results.

What the index will never see, whatever you write

The remote index is GitHub code search, so code search's exclusion rules are your exclusion rules. These are the ones that land hardest on a monorepo:

  • Files over 350 KiB, and any file carrying more than one line over 4,096 bytes. Your generated clients, your checked-in bundles, and that one enormous schema file are already gone.
  • Vendored and generated code. Binary files including PDFs. Anything not UTF-8 encoded.
  • Lines over 1,024 characters, which are truncated rather than dropped.
  • Everything outside the default branch.

Mark generated paths with linguist-generated in a root .gitattributes so the noise stops competing with your real code for retrieval slots.

Give Copilot a smaller room to search in

Every technique here shrinks the candidate set rather than improving the search over it. That is the only lever an application team owns, and it is a stronger one than prompt wording.

  • Trim files.exclude. The Copilot index skips anything excluded by files.exclude or by .gitignore. Dropping dist/, build/, generated clients, and fixtures can carry a repository back under 2,500 files, which is a change of index tier rather than a tidy-up.
  • Use a multi-root workspace. This is GitHub's own written recommendation for monorepos: a .code-workspace file listing the two or three services a developer actually touches gives the agent clear boundaries and cuts the indexable count at the same time.
  • Turn on chat.useCustomizationsInParentRepositories. If your developers open packages/checkout rather than the repository root, instruction discovery breaks silently. This setting is the documented fix, and it is the single most commonly missed setting on this page.
  • Point at files instead of searching for them. A #folder or #file reference beats a semantic search over 200,000 files every time. Teach #codebase rather than @workspace, which is ask-mode only and effectively legacy.

Make retrieval deterministic when it matters

Semantic search is a probability. On a repository this size you sometimes want a guarantee, and two tools give you one.

GitHub MCP server, search_code

Full code-search qualifier syntax, so path:, filename:, and language: return exactly what you named. Scope the server with GITHUB_TOOLSETS="repos,pull_requests,code_security" so its tool definitions don't eat the window they were meant to save.

Use for: surgical retrieval in a tree you can name.

A curated Copilot Space

Attach the ten to twenty files that define a subsystem as files, so they are in context for every query, and attach the monorepo itself as a repository for search fallback. That combination is the documented way to stop losing the retrieval lottery.

Use for: a subsystem your team asks about weekly.

Work it in this order

  1. Check the index tier in the Status Bar. If it says basic, stop here and build the remote index. Nothing else on this list matters until that is done.
  2. Open the References list on the weak answer. That takes ten seconds and it tells you whether retrieval or instruction was the problem.
  3. If the right file wasn't retrieved, narrow the question or write the path-scoped instruction file for that part of the tree.
  4. If the budget is the constraint, close the tabs and start a fresh chat before you change anything structural. That's free and it's immediate.
  5. Put the durable knowledge in a Space, with the handful of always-true documents attached as files rather than as a whole repository.

The fair objection, and it deserves a straight answer. On a repository nobody on the team has read end to end, how are you supposed to write path-scoped instructions for a tree you can't characterize yet? That's a genuine chicken-and-egg and I'm not going to wave it off.

You don't have to know the codebase first. Make Copilot draw you the map. Point a prompt file at a single flow, tell it to name every service that flow touches in order along with every place correctness depends on execution order, then read the answer against the References list. What it retrieved shows you where the seams are, and what it missed shows you where the instruction layer needs to go. You write that one file, the next question lands better, and then you do it again on the next flow. The characterization and the instruction layer build each other, one flow at a time.

Two questions to stop asking of a large repository. GitHub documents that Copilot cannot do comprehensive analysis across a codebase, naming “how many times is this function invoked?” and “rectify all bugs in this project” as examples, and it cannot answer questions about information outside the code such as who contributed to a file. These are exactly the questions people try first on a monorepo, they fail quietly rather than loudly, and the failure gets blamed on the model.

Spend the budget on purpose

Three habits, in order of how much they return.

  1. Close the editor tabs you aren't using. Open files are a line item on every request. That makes this the cheapest correction on the list.
  2. Start a new chat when the topic changes. History accumulates every turn, and an old thread spends your budget on a problem you already solved.
  3. Keep tier-1 files short enough to read aloud. If you can't, the content belongs in a path-scoped file where it costs nothing until it's relevant.

Diagnose from the References list, not the model picker

When an answer is weak, the useful question is never "which model should I have used." Work this order instead.

  1. Open the References list. What did it actually retrieve? This answers most questions in ten seconds.
  2. Was the right file absent? Then it's a retrieval problem. Scope the question narrower, or point at the file directly, or write a tier-2 instruction file for that path.
  3. Was the right file present and ignored? Then it's an instruction problem. Tell it what to care about in that part of the tree.
  4. Did you commit recently? The index lags. A file you added minutes ago may not be retrievable yet, and that's an operational fact worth planning around rather than a bug.
  5. Only now consider the model. It's the smallest lever in the room.

Read the budget instead of arguing about it

Everything on this sheet rests on one claim: context is a finite budget and you are already spending it. GitHub Copilot CLI will print that budget on request, which turns the claim into a receipt. If one engineer on your team stays skeptical, this is the fastest way to settle it.

The /context command reports the active model and the tokens in use against that model's total capacity, itemized:

Line itemWhat it tells you
System PromptFixed overhead. You don't control it.
Custom InstructionsThe files on this sheet. Your instruction layer is billed on its own line, separately from the conversation.
System ToolsTool definitions are charged whether or not you call them.
MCP ToolsSame rule, for anything you connected yourself.
MessagesYour turns, the responses, and every tool call and result. This is the line that grows.
Free SpaceWhat's left to work with.
BufferHeld back on purpose. See below.

At roughly 80 percent of capacity the CLI starts compacting in the background and holds back a buffer of roughly 20 percent so tool calls can keep running while it works. If usage reaches about 95 percent before compaction finishes, it pauses and waits. /compact does the same job on demand: it summarizes the conversation and replaces the history with that summary.

Two things to settle before you build on this. An organization can turn the Copilot CLI off in policy, so confirm your own tenant before you write it into a standard. And compaction is lossy by design, because a summary is smaller than what it replaced. A tight instruction layer spends less of the window in the first place, which pushes that summarization further away.

Measuring adoption without fooling yourself

The usage dashboard groups your population into adoption-phase cohorts, which beats a seat count. A seat count tells you who holds a license. A cohort tells you who changed how they work.

What the cohorts are good for

Finding where enablement will pay. A team clustered in early phases needs something different from a team that plateaued after the novelty faded.

What they can't see

These numbers can't tell you whether an accepted suggestion was any good, whether your senior engineers quietly stopped using it, or whether someone got genuinely faster rather than generating more code for a colleague to review.

The pattern worth watching for is what happens after a launch push. A contest or an internal campaign moves the population hard, and then a chunk of it settles back within a quarter. That's normal, and it's also the moment these cohorts start earning their keep, because the people who stayed changed a working habit and the people who drifted were riding the novelty. Aim your next round at that second group with something concrete, like a path-scoped instruction file for the tree they actually work in, rather than another all-hands demo.

Use the cohorts to aim, then go ask people. The dashboard is a map and it isn't the territory.
